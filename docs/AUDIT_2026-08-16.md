# AIC2026 Retrieval Audit — 2026-08-16

## Executive finding

The dataset itself is substantially complete, but the retrieval pipeline was **not actually using all BTC-provided support data** in the path used for the failing manual query.

Confirmed local audit:

- 177,321 keyframes
- 873 videos represented by keyframes
- 873 CLIP feature files, 512-D
- 873 mapping files
- 873 media-info JSON files
- 177,321 object JSON files
- persistent `IndexFlatIP` frame index with 177,321 rows

BTC explicitly defines Video as the official competition data and Keyframes, Objects, CLIP features and Metadata as supporting data. The system therefore must keep the official-video path intact while using the support data to improve retrieval and localization.

## Problems found

### 1. Object detection was effectively disabled

`dataset_index.py` wrote `object_path: ""` for every frame. Consequently the object component in `MultimodalReranker` received no object JSON and contributed zero signal.

This is a concrete implementation bug, not a model-quality question.

### 2. Metadata was opt-in instead of part of the normal retrieval path

`pipeline.py` could read metadata, but only when `--media-info-dir` was supplied. The failing manual command did not supply it, so BTC metadata was not used.

### 3. The supplied query was Vietnamese while the BTC visual space is OpenAI CLIP ViT-B/32

The official query spreadsheet contains an English `Trans` column. The previous direct command encoded only the Vietnamese query. For this CLIP space, using the organizer-provided English translation is the safer baseline.

The fix adds `--query-translated` and fuses the original query with the English translation, weighting the English embedding 0.80 and the original 0.20. The translated text is also used for lexical multimodal scoring.

### 4. Auxiliary SQLite evidence was also opt-in

Existing local `caption.sqlite` and `ocr.sqlite` artifacts were only used when explicitly passed. The fixed CLI auto-discovers them under `artifacts/` when present. These are treated as auxiliary evidence, not as replacements for BTC's official video data.

### 5. CLIP model variant warning

The previous default `ViT-B-32` + `openai` combination emitted a QuickGELU mismatch warning in the local environment. The fixed default explicitly selects `ViT-B-32-quickgelu` + `openai` to match the OpenAI CLIP ViT-B/32 family more explicitly.

## Source utilization matrix

| Source | Required role | Before audit | Fixed branch |
|---|---|---:|---:|
| Official videos | final source + temporal localization | yes | yes |
| Keyframes | retrieval index | yes | yes |
| CLIP ViT-B/32 features | dense retrieval | yes | yes |
| Keyframe ↔ original-frame mapping | correct output frame ID | yes | yes |
| Faster R-CNN objects | frame-level semantic reranking | effectively no | yes |
| Metadata | video-level semantic reranking | opt-in | default when present |
| Caption SQLite | auxiliary lexical evidence | opt-in | auto-discovered when present |
| OCR SQLite | auxiliary lexical evidence | opt-in | auto-discovered when present |
| BEiT-3 | optional experimental signal | optional | optional |

## Important methodological constraint

Do not declare a retrieval method correct merely because its CLIP score is high. For each query, evaluate in this order:

1. correct video;
2. correct event in the official source video;
3. correct original frame ID / temporal interval;
4. semantic keyframe quality;
5. rank profile R@1/R@5/R@20/R@50/R@100.

The competition metric implementation in `competition_metrics.py` already models the official Top-k R-Score structure.
